# Internationalization (i18n) Guide

All three demo chatbots (`ai-chatbot`, `api-chatbot` and `gw-chatbot`)
load their user-facing strings from JSON translation files. The active
language is selected at container startup with the `APP_LANG` environment
variable (default: `en`). `APP_LANG` is used instead of the standard POSIX
`LANG` variable to avoid colliding with the system locale.

## Layout

```
kubernetes/
├── app/i18n/                    # ai-chatbot (Network Intercept) translations
│   ├── en.json                  # ← default, also the canonical key list
│   └── pl.json
├── api-chatbot/i18n/            # api-chatbot (API Runtime) translations
│   ├── en.json
│   └── pl.json
└── gw-chatbot/i18n/             # gw-chatbot (AI Gateway Intercept) translations
    ├── en.json
    └── pl.json
```

> **`gw-chatbot` uses its own, smaller key set.** It was added later and its
> UI is simpler (chat + document list + upload), so it does **not** share the
> `_meta` / `page.*` / `flow.*` schema of the other two. Its sections are
> `app`, `ui`, `messages`, `errors` — see the table below. Keep each app's
> key set internally consistent; there is no cross-app key parity to maintain.

Translations live **inside the container image** (copied in at build
time). Switching language at runtime is therefore a `kubectl set env` +
rolling restart – no rebuild required, as long as the target translation
file is already baked into the image.

## Switching language on a running cluster

```bash
./scripts/switch-language.sh        # show current state + available languages
./scripts/switch-language.sh en     # English (default)
./scripts/switch-language.sh pl     # Polish
./scripts/switch-language.sh de     # any code with a matching <code>.json
```

The script:

1. Sets `APP_LANG=<code>` on all three deployments
2. Rolls a restart of each
3. Waits for the new pods to become ready
4. Prints a final summary

Deployments that are not present are skipped with a warning, so the script
works fine when only a subset of the three demos is deployed (e.g. the
optional `gw-chatbot` has not been rolled out yet).

If a translation file is missing inside the image, the application falls
back to `en.json` at startup and logs a warning.

## Adding a new language

1. Copy the English files as your starting template:

   ```bash
   cp kubernetes/app/i18n/en.json         kubernetes/app/i18n/<code>.json
   cp kubernetes/api-chatbot/i18n/en.json kubernetes/api-chatbot/i18n/<code>.json
   cp kubernetes/gw-chatbot/i18n/en.json  kubernetes/gw-chatbot/i18n/<code>.json
   ```

2. Translate **only the values**. Keep every key (including `_meta`)
   exactly as-is – the application looks up strings by key.

3. Update the `_meta` block in your new file (`ai-chatbot` and
   `api-chatbot` only – `gw-chatbot` has no `_meta` block and takes its
   `<html lang>` straight from `APP_LANG`):

   ```json
   "_meta": {
     "lang_code": "<code>",
     "html_lang": "<code>",      // BCP-47 tag, e.g. "de" or "fr-CA"
     "js_locale": "<locale>"     // for new Date().toLocaleTimeString(...)
   }
   ```

4. Rebuild and push the images so the new file lives in the next pod:

   ```bash
   ./scripts/deploy-app.sh          # ai-chatbot + api-chatbot
   ./scripts/deploy-gw-chatbot.sh   # gw-chatbot (optional third demo)
   ```

5. Switch:

   ```bash
   ./scripts/switch-language.sh <code>
   ```

## Key reference

The English files (`en.json`) are the canonical source of truth for the
key set. If you rename or add a key in one language, mirror that change
in every other language file (or new keys will simply render as
`undefined` / blank).

### `ai-chatbot` and `api-chatbot`

| Section          | Used in                                                 |
| ---------------- | ------------------------------------------------------- |
| `_meta`          | `<html lang>`, JS `toLocaleTimeString` locale           |
| `page.*`         | `<title>`, header, badges                               |
| `flow.*`         | Traffic-flow diagram steps                              |
| `welcome.*`      | First-message panel                                     |
| `input.*`        | Textarea placeholder, send button, attack button title  |
| `client.*`       | Browser-side JS messages (errors, demo labels, tags)    |
| `system.*`       | Server-side errors, log lines, default system prompt    |
| `attack_prompts` | (ai-chatbot only) malicious sample prompts for the demo |
| `status_bar.*`   | (api-chatbot only) top status bar                       |
| `side_panel.*`   | (api-chatbot only) right-hand panel headings            |

### `gw-chatbot` (different schema)

| Section     | Keys                                                                                          | Used in                                          |
| ----------- | --------------------------------------------------------------------------------------------- | ------------------------------------------------ |
| `app.*`     | `title`, `subtitle`, `mode`, `model_label`                                                    | `<title>`, header, mode badge, model badge       |
| `ui.*`      | `send`, `placeholder`, `upload`, `documents`, `no_documents`, `tools_used`, `guardrail`, `demo_attack`, `thinking` | Buttons, textarea, document panel, tool-call tags |
| `messages.*`| `blocked`, `no_content`, `tool_limit`                                                         | Guardrail block notice, empty reply, tool cap hit |
| `errors.*`  | `empty_message`, `gateway`, `no_file`, `bad_name`                                             | Server-side error responses                       |

There is **no `_meta` block** here – `templates/index.html` renders
`<html lang="{{ lang }}">` straight from `APP_LANG`, and timestamps use the
browser's own locale.

## Notes

- **System prompt for Gemini (ai-chatbot)**: `SYSTEM_PROMPT` env var
  takes precedence. If unset, the prompt is taken from
  `system.default_system_prompt` of the active language.
- **AIRS block messages (api-chatbot)**: `system.blocked_prompt_message`
  and `system.blocked_response_message` are returned to the browser
  whenever AIRS blocks content – translate these so end-users see the
  block reason in the chosen language.
- **Guardrail block message (gw-chatbot)**: `messages.blocked` is what the
  user sees when the AI Gateway returns HTTP 446 (AIRS guardrail blocked the
  prompt or the response). The block decision itself happens in the gateway,
  not in the app – the translation only affects how it is worded.
- **Logs**: log strings are also localized. Operators reading container
  logs may want to keep `APP_LANG=en` even if the UI runs in another
  language (in that case, deploy two replicas with different `APP_LANG`
  – or just translate the `system.log_*` keys carefully).
